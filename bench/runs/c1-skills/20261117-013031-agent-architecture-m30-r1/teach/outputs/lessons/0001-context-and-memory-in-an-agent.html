Context and memory in an agent

By the end of this lesson you can sketch a memory plan for the makerspace assistant: what sits in its context window, what it saves between sessions, and how it finds the right page in a long manual.

Warm-up 2 min

Two quick recall questions from the agent loop. Answer them in your head first, then open the answer.

Recall

When the model "calls" the booking tool, who actually runs the tool: the model or your program?

Check your answer

Your program does. The model only writes out a request ("call check_calendar with these arguments"). Your code runs it and hands the result back. Today this matters because whatever your program hands back becomes part of what the model reads next.

Recall

In a loop with five tool calls, how many separate model calls happen?

Check your answer

Six: one call to decide on each of the five tool calls, and one more to write the final answer after the last result comes back. Each is a separate call to the model. Today you will see what each of those six calls actually receives, and why that drives your cost.

The context window is working memory 5 min

The short version

The model can only "see" the text you hand it in the current call. That text is the context window. It has a size limit, and everything in it costs money. Anything not in it, the model does not know.

The detail

The official docs describe the context window as all the text the model can reference when it writes a response, including the response itself, and call it the model's "working memory" (Anthropic: context windows). It is separate from what the model absorbed in training. Training gave it general knowledge; the window holds this conversation's facts.

If you know how a computer works, the analogy is RAM versus disk. RAM is fast, small and wiped when the program ends. Disk is big and lasting but you have to go and read from it. A language model's window is the RAM. Everything we build for "memory" in this lesson is a way of using the equivalent of a disk.

Text is measured in tokens: the small chunks of text (often a short word or a piece of a longer one) that the model reads and writes. The window's limit is a number of tokens, and API usage is billed per token. So tokens are both the size limit and the price tag.

What fills the window in one call? The docs list it: the system prompt, every message so far, tool results, and the tool definitions, plus the model's own reply (Anthropic: context windows). Figure 1 shows the makerspace assistant partway through a request.

Check yourself

A student asks the assistant a question that needs a 3,000-token manual page. Which statement about the window is right?

The third option. Tool results are text in the window like any other: the model can use them only because they are there, and they count toward the limit and the bill. The model does not carry the machine manuals around in its head, which is why the page has to be fetched and placed in the window first.

What is kept between steps 6 min

The short version

Between steps, the model keeps nothing. Your program keeps the transcript and sends all of it again on every step. That is how the agent seems to remember what it just did, and it is also why long requests get expensive.

The detail

You learned that each step of the loop is a separate model call. Here is the consequence. The model does not hold a running thought between calls. Each call is like running a pure function: you pass in the full input, you get an output, and nothing is stored inside. The docs say it directly: each turn's input is the full prior history plus the new message, and the output becomes part of the next turn's input (Anthropic: context windows).

So the "memory" within a request is a Python list that your program keeps and resends. In the shape you will write later, it looks like this:

messages = [ {"role": "user", "content": "Is the laser cutter free Friday?"} ]

while True:
    reply = call_model(system_prompt, tools, messages)   # sends EVERYTHING
    messages.append(reply)                               # keep the model's turn
    if reply is a final answer:
        break
    result = run_tool(reply)                             # your code runs the tool
    messages.append(result)                              # keep the result for next call

Line by line: messages is the transcript. Each trip around the loop calls the model with the whole list (and the fixed system prompt and tool definitions). The model's reply is appended, the tool's result is appended, and the longer list goes out on the next trip. If you forgot the two append lines, the model would act as if each step were the first.

Worked example: the cost of resending

Suppose (made-up round numbers, to show the shape) the system prompt plus tool definitions is 1,000 tokens, and each loop step adds 1,500 tokens (a reply plus a tool result). Count what each call sends:

  1. Call 1: 1,000 + the student's short question, call it 1,000 in total sent.
  2. Call 2: 1,000 + 1,500 = 2,500 sent.
  3. Call 3: 1,000 + 3,000 = 4,000 sent.
  4. Call 4: 5,500 sent. Call 5: 7,000 sent.
  5. Total sent over five calls: 1,000 + 2,500 + 4,000 + 5,500 + 7,000 = 20,000 tokens, even though only about 7,500 tokens of "new" text were ever produced.

The total grows faster than the number of steps: each new step pays for everything before it, like re-reading a whole chat from the top every time you add one line. Prompt caching can make repeated text cheaper to pay for, but the docs are explicit that it changes the price, not whether those tokens count toward the window (Anthropic: context windows).

A common mix-up

"The model remembers what happened earlier in the loop, so it only needs the new result." It is tempting because the agent behaves as if it remembers. But the behaviour comes from your program resending the transcript. If you send only the new tool result, the model has no idea what question it is answering. The transcript is the memory, and your code owns it.

Check yourself

Your loop takes 8 steps and you want to cut cost. Which change would reduce the total tokens sent, without breaking the agent?

The third option. Because every step re-sends everything before it, a token added early is paid for again on every later call. Short tool results (say, the one relevant paragraph instead of the whole manual) save money at every step that follows. Sending only the newest result would be cheaper but would break the agent, and a larger window does not make anything cheaper.

Keeping the window lean 5 min

The short version

A fuller window is not a better window. More text costs more and can make the model worse at using it, so you aim to keep only what helps the next step.

The detail

Anthropic's engineers describe context as a finite resource with diminishing returns. As the number of tokens grows, the model's ability to accurately recall information from the context decreases, an effect they call context rot, and they set the goal as "the smallest possible set of high-signal tokens" that gets the job done (Anthropic: effective context engineering). The docs repeat the warning: as token count grows, accuracy and recall degrade (Anthropic: context windows). The effect is a gradual slope, not a cliff, and no source gives a magic size at which it starts.

So a long agent run needs housekeeping. Two moves from Anthropic's article:

  • Clearing old tool results. Their reasoning: once a tool has been called deep in the history, why would the agent need to see the raw result again? They call it one of the safest, lightest forms of trimming (Anthropic: effective context engineering). The 3,000-token manual page was needed to answer; after the answer, it can go.
  • Compaction. When a conversation nears the limit, the model summarizes it, and the summary replaces the long history. The summary keeps decisions and open problems and drops redundant tool output. The risk is that an over-eager summary drops something that matters later (same article).

A programming comparison: this is garbage collection plus checkpointing. You free what is no longer referenced, and when things get big you save a compressed snapshot and carry on from it.

Worked example: trim or summarize?

A student spends 20 turns with the assistant planning a project. Turn 3 returned a 3,000-token manual page about the laser cutter's material settings. Turn 18 is a question about booking time.

  1. Is the turn-3 page still needed to answer turn 18? No, it is about settings, and the student has moved on. That is a candidate for clearing.
  2. Is there something from turns 1 to 17 the assistant must not forget, such as "student is making a 6 mm acrylic sign"? Yes. Clearing would not keep it, but a summary would.
  3. So: clear the bulky page, and keep (or summarize into) a one-line fact. Cheap, and nothing important lost.
Check yourself

Which of these is most worth clearing from a long run's context?

The third option. Spent tool output is bulky and rarely needed again. The request and the tool definitions are what every later step depends on, so they stay. Rule of thumb: keep what the next step needs, drop what the last step consumed.

Between sessions: notes as memory 5 min

The short version

When a session ends, the window is gone. To remember something next time, your agent has to write it down somewhere outside the window and read it back later. Notes are the agent's disk.

The detail

This is the part with the most surprise for newcomers. A new session starts with an empty window. The model has no idea the student visited yesterday. Anything that should survive has to be saved by your system and then loaded into the new window.

Anthropic calls the pattern structured note-taking: the agent regularly writes notes to a place outside the context window and pulls them back in at later times. Examples in the article include a to-do list and a NOTES.md file the agent maintains. In one example, Claude playing a video game kept tallies across thousands of steps, and after its context was reset it read its own notes and carried on (Anthropic: effective context engineering).

The same idea is how this very workspace works: your tutor keeps NOTES.md and learning records, because it does not remember last week's session either.

Notes can be a file, a database row or a JSON blob. The design questions are what you save, when you write it, and when you load it.

Worked example: a student's training status

Sam completed the laser-cutter safety training on Monday. On Thursday Sam returns to book the cutter.

  1. What to save. A small record: {"student": "sam", "trained": ["laser_cutter"], "date": "Mon"}. Not the whole chat. Saved facts should be small, specific and likely to matter again.
  2. When to write. At the moment training is confirmed. Do not wait for the session to end, because sessions can end unexpectedly.
  3. When to load. At the start of Thursday's session, your program reads Sam's record and puts one line in the window ("Sam is trained on: laser_cutter"). The model never has to "remember"; it is told.
  4. Trust. The booking tool should still check the real records, because a note can go stale. Notes help the assistant; they are not the source of truth.
A common mix-up

"A bigger context window means the assistant remembers students." It is tempting because a large window feels like a large memory. But the window is emptied when the session ends, however big it is. Remembering across visits needs saved notes, and that is your design work, not a model setting.

Check yourself

The assistant should greet returning students by name and skip the safety quiz they passed. What is the minimum needed?

The first option. The session's window disappears, so the facts must live somewhere that does not: a saved record that your program loads into the next session's window. Retraining is out of scope and wrong for facts that change weekly, and a longer window only lasts for one session.

Retrieval: finding the right page 5 min

The short version

The machine manuals are far too long to put in the window. So the agent searches them and loads only the few pages that answer the question. That is retrieval.

The detail

Retrieval is the same idea as a database index or a search engine: do not scan everything, look up the likely pieces. The classic research version is retrieval-augmented generation (RAG). The original paper pairs a model's built-in knowledge, which it calls parametric memory, with an external searchable store of text it calls non-parametric memory (Lewis et al., 2020). The paper's stated motivation is that models store facts in their weights, which makes those facts hard to update and hard to trace to a source. A manual in a searchable store can be updated by swapping a file, and you can point to the page an answer came from.

Two ways to wire retrieval into an agent:

StyleHow it worksGood for
Up frontBefore the model runs, your code searches the manuals for the student's question and places the best pages in the window.Predictable, one-shot Q&A; simple and cheap to reason about.
Just in timeThe model gets a search_manuals tool and decides when to search, what to search for and which page to open.Questions where the first search is not enough; the model can try again.

Anthropic describes the second as keeping lightweight references (file paths, links, stored queries) and loading data at runtime with tools rather than pre-processing everything up front, and notes the trade-off: runtime exploration is slower, and without good tools the agent wastes context. Their own coding tool is a hybrid: some files are dropped in up front, while others are fetched on demand. Their advice is to "do the simplest thing that works" (Anthropic: effective context engineering).

One practical point for a long manual: how you cut it matters. A search tool returns pieces, so cut each manual into sections (for example "Laser cutter: material settings") and return a section, not the whole 80-page PDF. A section is small enough to fit and specific enough to help. And note what retrieval returns is a tool result, so everything from the earlier sections applies: it lands in the window, costs tokens, and can be cleared later.

Worked example: "What speed for 3 mm plywood?"
  1. The model reads the question and calls search_manuals("laser cutter plywood speed").
  2. Your program searches the section index and returns the top three section titles with a two-line preview each (about 150 tokens, not 3,000).
  3. The model picks "Laser cutter: material settings" and calls open_section with that id.
  4. The 600-token section comes back, and the model answers, quoting the setting and naming the section so the student can check it.

Total new text: about 750 tokens, against 80 pages loaded blindly. This is the loop you already know, used as a lookup. The cost of the extra step is one more call, which resends the transcript, so retrieval trades a bit of loop overhead for a much smaller window.

A common mix-up

"Retrieval means the model has learned the manuals." It is tempting because the answers are correct. But nothing was learned: the page was placed in the window for this call, and once it is cleared, or the session ends, the model has no trace of it. That is a feature: you update the manual and the next answer uses the update, with no retraining.

Check yourself

The student asks something that the first search does not answer. Which design copes best?

The third option. When the first result is not enough, an agent with a search tool can reformulate the query and try again, loading only what helps. One fixed up-front search is cheaper and fine for easy questions, but cannot recover from a weak first result. Pasting everything in pays for the whole library on every call.

Worked example and practice 5 min

Now put the three layers together: the window, notes and retrieval. First a worked memory plan for one feature, then you do a similar one.

Worked example: "Book me the laser cutter for Friday afternoon"
  1. Start of session (notes, load). The program loads Sam's saved record and puts one line in the window: "Sam is trained on: laser_cutter." The record is small, so the cost is tiny, and it is the same every session so it is predictable.
  2. During the request (window). The model calls check_calendar for Friday. The calendar JSON comes back, and your program trims it to the free slots before it goes into the window, so the model does not read 200 irrelevant bookings.
  3. Only if needed (retrieval). If Sam asks "what is the maximum booking length?", the model searches the policy manual and loads that one section. If Sam does not ask, nothing is loaded and nothing is paid for.
  4. After booking (window, trim). The calendar result is no longer needed once the booking tool has confirmed, so it can be cleared if the conversation goes on.
  5. End of session (notes, write). The program saves "Sam booked laser_cutter Fri 2 pm" if the assistant should be able to refer to it later. The booking system remains the real source of truth; the note is a convenience.

Plan the same three layers for this request: "I want to 3D print a bracket. What do I need to know, and can I use the printer tomorrow?" The printer needs its own training. Step 1 is given: at session start, load the student's saved record. Write down, in a few lines each:

  4. What, if anything, is saved at the end, and why is it not the source of truth?
Show a solution

2. Window. The student's question and the one-line record ("trained on: laser_cutter", so not the printer). The calendar check for tomorrow is trimmed to the printer's free slots only.

3. Retrieval. The question has two parts, so just in time suits it: the model searches "3D printer bracket guidelines", opens the one section on material and print settings, and separately sees from the record that printer training is missing. It can then fetch the "printer training" section and tell the student how to get trained. Up front retrieval would have guessed one search before knowing about the missing training.

4. Save. Something like "Sam asked about printer training on Thursday", so the next visit can follow up. It is not the source of truth because the real training records are held by the makerspace and can change; the booking tool should check them.

Summary 2 min

  • The context window is the model's working memory: only what is in it this call can be used, and every token in it is billed.
  • Between steps, the model keeps nothing. Your program resends the transcript each call, so long runs cost more than the step count suggests.
  • Keep the window lean: clear spent tool results, and summarize when a conversation gets long. More text can reduce recall.
  • Between sessions, only what you save survives. Notes are small records written outside the window and loaded back in.
  • Retrieval fetches only the relevant pieces of a library too big for the window, either up front or just in time through a search tool.
