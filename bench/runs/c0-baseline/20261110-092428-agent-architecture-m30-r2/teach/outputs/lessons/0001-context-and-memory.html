Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context window, in saved notes, or in a searchable store, and give a reason.

Why this matters for you

Your assistant has to answer from long machine manuals, remember each student's training status between visits, and stay inside a small model budget. All three problems are context and memory problems. At your design review, "what does it keep, where, and why?" is the question you will be asked.

The context window 5 min

Start with a plain example. You are taking an open-book exam, but the desk is small. Whatever fits on the desk, you can read. Everything else is in the library down the hall, and you cannot use it unless someone fetches it and puts it on the desk.

A language model works like that. The context window is the text the model can read when it writes its next output: the desk. It is measured in tokens, the small chunks of text (a short word, or part of a longer one) that the model reads and writes. The window has a maximum size, and the sizes differ from one model to another (Claude documentation: context windows). The model has no other view of the world. If something is not in the window, the model does not know it, even if it was said ten minutes ago.

For an agent, the window holds several kinds of things at once:

  • the system prompt: the standing instructions ("You are the makerspace assistant. Never book a machine without checking training.");
  • the tool descriptions: the names and explanations of check_calendar, search_manuals and the rest, which is how the model knows they exist;
  • the message history: the student's questions, the model's earlier replies, and its tool requests;
  • the tool results: whatever each tool sent back.

Why the size matters twice

First, the window is a hard limit: if the content does not fit, the call fails or something must be dropped. Second, and more important for your budget, you pay for tokens. Model usage is typically billed per token read and written, so a bigger window being filled means a bigger bill on every call.

There is also a quality cost. Anthropic's engineering team describes context rot: as the number of tokens in the window grows, the model's ability to recall information from it tends to decrease. They treat context as a finite resource with diminishing returns, and say the goal is the smallest set of high-signal tokens that makes the desired result most likely (Effective context engineering for AI agents). So "put everything in" is not a safe default. It is slower, costlier and can make answers worse.

Some models now have very large windows. A big window raises the limit, not the cost per token or the effect of context rot, so the design question stays the same.

What is kept between steps 6 min

Here is the idea that surprises most people. The model itself keeps nothing from one call to the next. Each call starts blank. What looks like memory inside a run is the program resending the whole conversation every time.

Think of a clerk who forgets everything the moment you leave the counter. To keep a conversation going, you hand over a growing stack of paper each time: "Here is everything we have said so far. What next?" That is the agent loop. At each step the program builds the window again: system prompt, tool descriptions, all earlier messages and tool results, plus the newest result. Then it calls the model, which reads the lot from the top.

So what is kept between steps is exactly what the program chooses to put back into the next window. By default, that is everything. The program is the memory, and the program can choose differently.

Why this drives cost

Because every call rereads the whole stack, the tokens you pay for add up faster than the conversation grows. Here is a made-up but typical shape, for a request that needs three tool calls:

Worked example: cost of a three-tool request (illustrative numbers)

Suppose the setup is 2,000 tokens (system prompt and tool descriptions), and each step adds 500 tokens (the model's request plus the tool result). The model is called four times: three to request tools, one to write the final answer.

  1. Call 1 reads 2,000 input tokens.
  2. Call 2 reads 2,000 + 500 = 2,500.
  3. Call 3 reads 2,000 + 1,000 = 3,000.
  4. Call 4 reads 2,000 + 1,500 = 3,500.
  5. Total input read: 2,000 + 2,500 + 3,000 + 3,500 = 11,000 tokens. The final window is only 3,500 tokens, but you paid for 11,000.

Two practical lessons follow. A big tool result is expensive twice over: it is read once when it arrives, and then again on every later call in the run. And the setup is paid for on every single call, so a long system prompt or a dozen tool descriptions the assistant rarely uses is a standing cost. (Some providers offer discounts for repeated, unchanged prefixes, called prompt caching. It helps with the setup but does not remove the growth.)

A common mix-up

"The model remembers the earlier steps, so resending them is just a formality." It is tempting because chat apps feel continuous. But the model is called fresh each time, and only sees what is in the window. Leave out step 2's result, and the model has no idea step 2 happened. That is also your power: you decide what it sees.

Keeping the window small 5 min

If the program chooses what goes back in, it can keep the window lean. Anthropic describes three techniques for long tasks: compaction, structured note-taking, and splitting work across sub-agents (summarized by a readthedocs guide on the post). Today we cover the first two, and the third belongs to a later lesson on multiple agents. Before those, there is a cheaper fix that comes first.

1. Make tools return less

The same Anthropic post advises that tools should return token-efficient information (Effective context engineering). Your check_calendar tool should not return the whole month of bookings when the student asked about Friday; it should return Friday's slots. Your search_manuals tool should return three short passages, not the whole manual. This is the biggest saving, and it costs nothing in quality.

2. Compaction

Compaction means summarizing an old part of the conversation and replacing it with the summary when the window gets full. Imagine a long chat with a student who is planning a project that needs three machines. After twenty exchanges, the program asks the model for a short summary ("Student is building a box from 3 mm acrylic; laser cutter booked Friday 2 pm; still needs 3D printer slot") and restarts the window with that summary instead of the full history. The cost is that detail is lost, so what goes in the summary matters.

3. Notes outside the window

The agent can write key facts to a file or database outside the window and read them back later. Anthropic calls this structured note-taking. Even a short running list of "decisions so far" survives compaction, because the program re-reads it when needed. This idea is also the bridge to the next section.

What is kept between sessions: notes 5 min

Now step up a level. A session is one run of the assistant for one student, from the first question to the end of the conversation. When it ends, the window is discarded. The next day the student opens the assistant again and the window starts empty: system prompt, tool descriptions, and nothing else.

An everyday example: a doctor's receptionist who has no files. Every time you walk in, you must say who you are, your allergies, and what happened last visit. A receptionist with a file cabinet looks you up in seconds. For your assistant, the file cabinet is memory: information saved outside the window, and loaded back in when it is useful.

Anthropic's "building effective agents" guide describes the basic unit of an agent system as a model augmented with retrieval, tools and memory, and notes that current models can generate their own search queries and decide what information to retain (Building effective agents). Memory, in other words, is a capability you add around the model. It does not come with it.

Designing the notes for your assistant

Two questions decide a good memory:

  • What is worth saving? Facts that stay true and that you would otherwise have to ask again: a student's completed trainings, a stated preference ("prefers evening slots"). Not the full transcript, which is large and mostly noise.
  • Who is allowed to change it? Training status is a safety record. It should be written by a trusted system (the makerspace's own records), not by the model's guess from what a student said. Notes the model writes itself are best for low-stakes things like preferences.

At the start of each session, the program loads the relevant notes into the window. That costs tokens, so load only this student's short record, not everyone's.

A common mix-up

"A long context window is a memory." It is tempting because both let the assistant "know" things. But a window is gone when the session ends, and every token in it is paid for on every call. Memory is a store you write to and read from. Use the window for what the current task needs, and the store for what must outlive it.

Retrieval: finding the right page 5 min

Notes remember facts about students. The manuals are a different problem: they are huge, they do not change by student, and most of any manual is irrelevant to any question. Retrieval means searching a store for the few pieces that matter for this question and placing only those in the window. The model then answers from text that is in front of it, instead of from guesses. (You noticed chatbots stating outdated facts confidently; retrieval is one remedy, because the answer comes from your current manual.)

A library example: you do not carry the library to your desk. You ask the librarian, who returns the two relevant pages. The steps for the assistant are:

  1. Prepare once, ahead of time. Split each manual into chunks, passages of a paragraph or a section, each kept with its machine name and page number.
  2. Search at question time. The search_manuals tool takes a query and finds the best-matching chunks. Matching can be by keywords, by meaning, or both.
  3. Return a few. The tool sends back, say, the top three chunks with their sources.
  4. Answer and cite. The model writes the answer from those chunks and names the manual and page, so a student can check.

Notice that retrieval is just another tool in the agent loop you already know. The model asks for a search, the program runs it, and the chunks come back as a tool result. This is the "just in time" approach: Anthropic describes agents keeping lightweight references and loading data into context only when needed, instead of loading everything up front (Effective context engineering).

Where retrieval goes wrong

  • Chunks too big waste tokens, the same problem as the 6,000-token result above.
  • Chunks too small lose context: "Set speed to 40" is useless without knowing the material and machine it refers to. Keeping the heading and machine name with each chunk fixes much of this.
  • Wrong chunks returned. The model then answers from the wrong page, perhaps with confidence. Always have it cite the page, and let it say "not found" when nothing matches.

Worked example

Riley's teammate wants to store "Which machines does this student's club project use?" Where should it go?

  1. Needed beyond this session? Probably yes: the student will return to the same project, so asking again each time is a nuisance.
  2. How big? One line per project. Small enough to load whole at the start, so no retrieval is needed.
  3. How risky if wrong? Low. A wrong guess costs a clarifying question, not a safety problem. So the model may write this note itself.
  4. Decision: a short saved note, written by the assistant, loaded at the start of the session.
Your turn

The sponsor asks you to add the makerspace's 40-page safety handbook, and says the assistant must always know the rule "closed-toe shoes only." Decide where (a) the shoes rule and (b) the full handbook go. Start with the first question: is each one needed on every call? Then think about size and about what happens if the model misses it.

Show a solution

(a) The shoes rule is one sentence, needed on every conversation, and a safety matter, so it goes in the system prompt, always in the window. (b) The full handbook is 40 pages, and most questions need only one rule from it, so put it in the searchable store and retrieve the relevant chunks. The fixed one-line rule can be duplicated in the prompt; the details stay in the store.

Summary 2 min

  • The context window is everything the model can read on one call, measured in tokens. It is limited and every token costs money.
  • Between steps, the model keeps nothing: the program resends the setup and all earlier steps each time, so cost grows faster than the conversation. Trim tool results first; then compact.
  • Between sessions, the window is gone. Facts that must last go to a saved store and are loaded back in.
  • Retrieval puts only the few relevant chunks of a large store into the window, using a search tool.
