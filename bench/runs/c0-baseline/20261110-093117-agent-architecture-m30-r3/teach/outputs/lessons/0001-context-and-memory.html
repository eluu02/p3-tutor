Context and memory: what an agent sees, keeps and looks up

By the end of this lesson you can say, for any piece of information in the makerspace assistant, whether it belongs in the context, in saved notes, or in a searchable manual, and give the reason.

Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, on a small budget. All three jobs come down to one question: what text does the model get on each call? This lesson gives you the vocabulary to answer it in a design review.

Warm-up 2 min

Two questions from the agent loop, answered from memory before you read on.

Recall

A student asks, "Is the laser cutter free tomorrow, and do I need training?" The model asks for the calendar, then the training record, then writes its answer. Who runs the two tools, and how many separate times is the model called?

Check your answer

The program around the model runs the tools; the model only writes a request. The model is called three times: once to ask for the calendar, once to ask for the training record, once to write the answer. Each call is separate, which is the key fact for today: if every call is separate, how does call three know what happened in call one? That is the whole lesson.

The context window: everything the model sees 5 min

Start with an everyday case. Imagine a clerk at the makerspace desk who has no memory at all. Every time you speak to them, you must hand over a single sheet of paper with everything they need: the rules, the question, and anything they looked up. They answer from that sheet alone, then forget it.

A language model works like that clerk. A token is a small chunk of text, often a short word or part of a word; models read and write text as tokens. The context window is the limit on how many tokens the model can work with in one call, counting what goes in and what it writes out (Anthropic: context windows). The context is the text actually placed in that window for one call: the "sheet of paper".

For the makerspace assistant, one call's context holds these parts:

  • the system prompt: your instructions ("You are the makerspace assistant. Never book a machine for an untrained student.");
  • the tool descriptions you wrote;
  • the conversation so far: the student's messages, the model's earlier replies and tool requests, and the tool results.
A common mix-up

"The model remembers what we said earlier." This feels true because chatbots seem to remember. They do not: the program sends the earlier messages again each time. If your code sent only the newest question, the model would answer as if it had never met the student. Memory in an agent is something your program builds, by deciding which text goes into the next call.

Between steps: the transcript grows 5 min

Now connect this to the agent loop. Inside one task, the program keeps a list of messages, the transcript. After each step it appends two things: what the model asked for, and what the tool returned. Then it sends the whole transcript to the model again. That is how call three knows what happened in call one: it reads it.

This has a cost you can calculate. You pay for every token sent in, on every call, so the early parts of the transcript are paid for again and again. Here are illustrative numbers (invented for teaching; your real counts will differ) for the question "Is the laser cutter free tomorrow at 3 pm, and do I need training?"

CallWhat is added before itTokens sent in
1System prompt, tools, question: 1,0501,050
2Tool request 50 + calendar result 4001,500
3Tool request 50 + manual page 3,0004,550
4Tool request 50 + training record 1004,700

The context never exceeded 4,700 tokens, yet the run sent 1,050 + 1,500 + 4,550 + 4,700 = 11,800 tokens in. The 3,000-token manual page was paid for twice, in calls 3 and 4, even though the model needed it only to decide what to ask next. Models are priced by tokens, so this is why the lesson matters to your budget (Anthropic: context windows explains the window and its limits).

There is a second cost besides money. Anthropic's engineering team describes context as a finite resource with diminishing returns: as the window fills, a model's ability to recall details from it tends to fall, an effect they call context rot, so the goal is the smallest set of high-signal tokens that makes the right answer likely (Anthropic Engineering: Effective context engineering for AI agents).

A common mix-up

"A bigger context window means I can stop worrying about what goes in." Tempting, because a big window sounds like a big memory. But a bigger window only raises the ceiling. Every token inside still costs money on every call and still competes for the model's attention. A window big enough for a whole manual is a poor reason to send the whole manual.

Check yourself

The third option. Each of the five calls re-sends its whole context, so the run's input is the sum of five context sizes, which is more than 6,000.

Keeping the context small 4 min

Because the transcript is just a list your program controls, you can edit it. Three simple moves, in order of how much effort they take:

  1. Make tool results small. A search_manuals tool that returns the best 800-token passage is better than one that returns a 3,000-token page. Anthropic's guidance is that tools should return token-efficient information (Anthropic Engineering).
  2. Drop what is no longer needed. Once the model has used the manual page to decide, your program could replace it with a one-line summary, such as "Laser cutter manual: needs level 2 training".
  3. Compact. When a long task nears the limit, ask the model to summarise the transcript so far, then start a fresh context with that summary. Anthropic calls this compaction and lists it as a technique for long tasks (Anthropic Engineering).
Most makerspace questions are short, four or five calls. Move 1 is almost always the one that pays for you; compaction matters for long sessions such as a coding agent, not for a booking question.

Each move trades something: dropping or summarising text can lose a detail you needed later. Decide what the model must still be able to see to finish the task, and cut the rest.

Between sessions: notes 5 min

A session is one conversation with one student. When it ends, the program throws the transcript away unless you save it. So on Monday the assistant tells Sam, "You still need laser cutter training"; on Thursday Sam returns, the context starts empty, and the assistant has no idea Sam finished training on Wednesday.

The fix is plain: write what matters to storage outside the model, and read it back into the context at the start of the next session. This is memory as notes. A note can be a row in a database, a JSON file or a text file; the model does not need to be involved in storing it. Anthropic describes structured note-taking as the agent regularly writing notes to storage outside the context window and pulling them back in later (Anthropic Engineering).

Two design questions decide whether notes help or hurt:

  • What to save. Save facts that stay useful and cannot be recomputed cheaply: training status, preferences, open bookings. Do not save the whole chat; it is long and mostly stale.
  • Where the truth lives. A note copies a fact. Machine availability changes hourly, so a saved copy goes stale. Keep that one in the booking system and let the assistant call the calendar tool every time. Training status is better held in the makerspace's own record than in the assistant's private note, so it cannot drift from the official answer.

Retrieval: finding the right page 5 min

The manuals are the third kind of knowledge. The laser cutter manual may run 200 pages, which is far too much to send on every call, and you do not need all of it to answer "What focal height do I use for 3 mm acrylic?". You need the one page that says so.

Retrieval means searching a collection for the few pieces that match the question and putting only those in the context. The usual recipe, often called retrieval-augmented generation (RAG):

  1. Prepare once, ahead of time. Split each manual into chunks of a few paragraphs, and index them so they can be searched.
  2. Search at question time. Turn the question into a search, using keyword matching, embeddings (numbers that let a computer find text with a similar meaning), or both.
  3. Return the best few chunks as a tool result, with the manual name and page.
  4. The model answers from them and can cite the page.

In an agent, retrieval is simply another tool: search_manuals(machine, query). The model decides when to call it, so it follows the same loop you already know. Anthropic calls this just-in-time retrieval: the agent keeps light references and loads data into context only when needed, instead of preloading everything (Anthropic Engineering).

Chunking has a known weakness: a chunk cut from the middle of a manual can lose its meaning. A chunk saying "Set it to 12 mm" does not say which machine or setting. Anthropic's contextual retrieval technique adds a short explanation of where the chunk comes from before indexing it, to reduce such failures. A simpler version you can do yourself is to store the machine name and section title with every chunk.

A common mix-up

"Retrieval means the assistant has learned the manuals." Tempting, since it answers manual questions well. But nothing is learned: the model has not changed. Each answer comes from chunks put in front of it on that call. If the search returns the wrong chunk, the model answers from the wrong page, so retrieval quality sets the ceiling on answer quality.

Worked example and practice 5 min

Worked example

Place these three facts: (A) "Students under 18 need a staff member present at the laser cutter," (B) "Priya's last booking was the vinyl cutter," (C) the 40-page vinyl cutter manual.

  1. Fact A. It is short, always true and applies to every question about that machine. That fits the system prompt, which is sent on every call.
  2. Fact B. It is about one student and must outlive the session. That fits a saved note, read into the context when Priya starts a new session.
  3. Fact C. It is large and only a few paragraphs matter for any question. That fits the retrieval index, with search_manuals returning the best chunks.
  4. Check the cost. Sending C on every call would add its full size to every call. Putting only the relevant chunks in, once, adds a few hundred tokens.
Your turn

Part 1. Place these: (D) "The CNC router is booked Tuesday 2 to 4 pm," (E) "Jo is allergic to a resin and asked not to be assigned the resin printer." The first step is done for you: ask for each fact how long it lives and how fast it changes.

Part 2. Redo the token table from section 2, but with search_manuals returning an 800-token chunk instead of 3,000. What is the total number of tokens sent in over the four calls?

Show a solution

Part 1. D changes fast and belongs to the booking system, so use the calendar tool each time; a saved copy would go stale. E is about one person and must last, so it is a saved note, read in at the start of Jo's sessions.

Part 2. Call 1 sends 1,050. Call 2 sends 1,050 + 50 + 400 = 1,500. Call 3 sends 1,500 + 50 + 800 = 2,350. Call 4 sends 2,350 + 50 + 100 = 2,500. Total: 1,050 + 1,500 + 2,350 + 2,500 = 7,400, against 11,800 before, a saving of 4,400 tokens from one change to one tool.

Summary 2 min

  • The model keeps nothing between calls. The context window holds everything it can use on one call: system prompt, tool descriptions and the transcript.
  • Within a task, the transcript grows and is re-sent every call, so big tool results cost money repeatedly and can crowd out attention. Keep results small; trim or compact when needed.
  • Between sessions, nothing survives unless you save it. Notes are short facts written outside the model and read back at the start. Live facts stay in their source and are fetched by tools.
  • Retrieval is a search tool over chunked manuals that puts only the few best chunks into the context.

Say it in your own words: without looking, explain to a teammate why Sam's training status on Thursday depends on something your program did on Wednesday, and why the assistant should not receive the whole laser cutter manual on every call.
