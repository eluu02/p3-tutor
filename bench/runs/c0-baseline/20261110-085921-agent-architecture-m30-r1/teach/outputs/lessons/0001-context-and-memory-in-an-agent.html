Context and memory in an agent

By the end of this lesson you can say what your makerspace assistant sees at each step, what it keeps between steps and between sessions, and when to use notes or retrieval to give it memory.

The context window: what the model sees 5 min

Start with an everyday case. You hire a helper who has no memory at all. Every time you speak to them, you must hand over a single sheet of paper with everything they need: their instructions, the conversation so far and any documents. They read the sheet, write a reply, and the sheet is thrown away.

A language model works like this helper. Each model call receives one block of text and produces a reply. The model keeps nothing inside itself between calls. The block of text it reads is the context. A token is the small chunk of text, often a word or part of a word, that the model reads and writes. The context window is the most tokens the model can handle in one call, and it covers both what goes in and what the model writes back (Claude docs: context windows).

For your assistant, the context holds four kinds of things:

  • the system prompt: the standing instructions ("You are the makerspace assistant. Never book a machine unless the student is trained.");
  • the tool descriptions: the name and purpose of check_calendar, search_manuals and the rest;
  • the message history: the student's questions, the model's tool requests and every tool result so far;
  • anything else you choose to add, such as notes or retrieved manual pages.

Two limits follow. First, the window has a maximum size, and a request whose input is too long is rejected (Claude docs). Second, a bigger window does not mean the model uses all of it equally well. Anthropic describes context rot: as the number of tokens grows, the model's ability to recall details from them goes down, because the model has a limited "attention budget". Their guidance is to find the smallest set of high-signal tokens that makes the result likely (Anthropic: Effective context engineering for AI agents). A research paper found something similar: models did best when the relevant passage was at the start or end of a long input and worse when it was in the middle (Liu et al., "Lost in the Middle").

You are billed for tokens, in and out, so a lean context is also a cheaper one. This is the link between context and your sponsor's budget.

Between steps: the context grows 6 min

Inside one request, the agent loop has several steps, and each step is a separate model call. So how does the model "remember" step 1 at step 3? It does not. Your program keeps a list of messages and sends the whole list again on every call. After each tool runs, the program appends two things: the model's tool request and the tool's result. Then it calls the model again with the longer list.

Here is one request, "Is the laser cutter free tomorrow at 3 pm, and do I need training?", with invented but realistic sizes:

CallAdded since the last callTotal sent in
1System prompt, tools, question: 1,5501,550
2Tool request 80 + calendar result 4002,030
3Tool request 80 + manual page 3,0005,110
4Tool request 80 + training result 2005,390

The context at call 4 is about 5,400 tokens. But you were billed for input on every call: 1,550 + 2,030 + 5,110 + 5,390 = 14,080 tokens. The 3,000-token manual page was sent twice, in calls 3 and 4. That is why a long page, once it enters the history, keeps costing money for the rest of the request. (Providers offer ways to discount repeated text, such as prompt caching, but the principle stays: what you put in, you keep paying for.)

So what do you do when the history gets too big? Anthropic describes three techniques for long tasks (Anthropic):

  • Compaction: replace the old part of the history with a short summary and carry on. You keep the gist and lose the detail.
  • Trimming tool results: return only the useful part of a tool's output, such as the three relevant lines of a manual, not the whole page. Tools should return token-efficient output.
  • Sub-agents: hand a side task to a separate model call with its own fresh context, and take back only a short result. This is the start of multi-agent design, which a later lesson covers.

For a makerspace question, most requests are short, so you may never need compaction. Trimming tool results is the cheap habit to start with.

A common mix-up

"A bigger context window means the assistant can just keep everything." It is tempting because the window is the visible limit. But a request that fits can still be expensive (you pay for every token on every call) and can still be less accurate (context rot). The window tells you what is possible, not what is wise.

Between sessions: nothing, unless you save it 4 min

A session here is one conversation or request, from the student's first message to the final answer. When it ends, the message list your program held disappears. The next session starts with a fresh context: system prompt, tools and the new question. The model has not changed, and it remembers nothing (Claude docs: memory tool describe memory as something your application provides).

So every kind of "memory" an agent has is the same trick: save something outside the model, and later put the right part of it back into the context. There are three places to look:

KindWhere it livesMakerspace example
Working memoryThe context, this request onlyThe calendar result from step 2
NotesA file or database your program keeps per student"Riley: laser cutter trained on 3 March"
RetrievalA searchable store of documentsThe 200-page laser cutter manual

Notes and retrieval look similar but answer different needs. Notes hold facts the assistant learned or recorded, which change over time and are usually small. Retrieval searches a big body of text that already exists and that you do not want in the context all at once.

Notes as memory 5 min

Think of a mechanic's job sheet: at the end of a shift they write what they did and what is left, and the next shift reads it first. Structured note-taking is the same for an agent. It writes notes to storage outside the context window and reads them back later (Anthropic).

Anthropic's memory tool is one design for this. Claude issues file commands (view, create, edit and so on) on a /memories directory, and your code carries them out and decides where the files really live, for example one folder per student. When the tool is on, the model checks the memory directory before starting work (Claude docs: memory tool). Notice that this is the agent loop again: memory is just more tools, run by your program.

Worked example: a student's training status

Session 1 (March): Riley completes laser cutter training. Session 2 (April): Riley asks to book the laser cutter.

  1. At the end of session 1, the model requests a tool call that writes /memories/riley.md with "Laser cutter training: done 3 March." Your code saves it to disk.
  2. Session 2 begins with an empty history. The model, following the system prompt, first requests a view of /memories/riley.md.
  3. Your code returns the file text. It joins the history, costing only a few dozen tokens.
  4. The model now knows Riley is trained and calls the booking tool.

For a fact like training status, though, think about whether a note is the right home. If the makerspace already has a training database, the safest design is a tool that queries it, so the answer is always current. Use notes for what has no other home, such as "Riley prefers mornings."

A common mix-up

"Saving everything is safest." Notes are loaded into the context, so a pile of old notes brings back the cost and context-rot problems from section 2. Save little, keep notes short and date them, since a note can go out of date just like the chatbot fact you noticed earlier. Never save a student's private details you do not need.

Retrieval: finding the right page 5 min

A laser cutter manual may run to 200 pages, about 100,000 tokens. Pasting it into every request would be slow, costly and prone to context rot. Retrieval means searching the documents first and putting only the best matches into the context.

The usual steps (Anthropic: Contextual Retrieval):

  1. Prepare once, ahead of time: split each manual into chunks (a few paragraphs each) and build a search index over them.
  2. Search at question time: turn the student's question into a search, and take the top few chunks.
  3. Answer from them: put those chunks in the context and let the model answer, citing the chunk.

Search can match words (keyword search) or meaning (embeddings, which turn text into numbers so that similar meanings land close together). The Anthropic post combines both and notes that chunks cut loose from their document can lose their meaning: a chunk saying "the maximum speed is 40" does not say which machine it is about. Adding a line of context to each chunk before indexing reduced missed chunks in their tests (Anthropic; these are the company's own measurements).

Another way, which Anthropic calls just-in-time retrieval, is to give the agent a search tool and let it fetch what it needs as it goes, instead of loading everything first (Anthropic). For your assistant, search_manuals(machine, query) is exactly that: a retrieval step wrapped as a tool. The quality of the tool's description decides whether the model calls it at the right time.

Worked example and practice 6 min

Worked example: where does each piece go?

Decide for each item whether it belongs in the always-on context, in notes, or in retrieval.

  1. "Be polite, never book an untrained student." It applies to every request and is short, so it goes in the system prompt.
  2. The bandsaw manual. It is long, existing, and only a few paragraphs matter per question, so it goes in retrieval.
  3. "Sam asked us to remind him about the 3D printer queue." It is a small fact about one person that changes over time, so it goes in notes for Sam.
  4. Tomorrow's laser cutter bookings. It changes by the minute and the calendar already holds it, so it is neither: it is a tool call to the calendar, fetched fresh.

Summary 2 min

  • The model sees only its context for each call. The context window is the cap on that, and a fuller context costs more and can be recalled less well.
  • Between steps, your program resends the growing message list on every call, so large tool results are paid for again and again.
  • Between sessions the model keeps nothing. Memory means saving something outside the model and putting the right part back into the context.
  • Notes hold small facts the assistant records. Retrieval searches big documents and returns a few chunks. Live facts belong behind a tool.

Say it in your own words: Without looking, explain to a teammate how the assistant can know on Tuesday that a student was trained last month, and why you would not paste the whole manual into every request.
