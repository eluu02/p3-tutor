Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context for this step, in saved notes for the next visit, or in a manual that is searched on demand.

The context window 6 min

Start with a concrete case. A student types: "Is the laser cutter free tomorrow at 3 pm?" Your program calls the model. What does it send? Not just the question. It sends a bundle of text, and the model reads only that bundle.

That bundle is the context: all the text the model is given for one call. The context window is the limit on how much text (counted in tokens, the small chunks of text the model reads and writes, roughly three-quarters of a word each) the model can take in and work with at once. Anthropic's guide describes it as the model's working memory for a conversation, and notes that as a conversation grows you eventually approach its limit (Claude docs: context windows).

Two facts follow, and both matter for your budget.

First, the window is finite. Anthropic's engineering team calls context a limited resource with diminishing returns: the model has an "attention budget," so the goal is the smallest set of high-signal tokens that gets the job done, not the largest set that fits (Anthropic: Effective context engineering for AI agents).

Second, you pay for what you send. Usage is billed by tokens, and the whole stack in Figure 1 is sent again on every call. A long system prompt is a cost on every step of every request.

A common mix-up

"Models now have huge windows, so I can paste in every manual and skip the clever parts." It is tempting because the window does hold a lot. But the manuals would be re-sent, and re-billed, on every call, and a crowded context makes it harder for the model to pick out the one relevant paragraph. A bigger window raises the ceiling; it does not remove the need to choose what goes in.

Check yourself

The assistant answered a question at step 3 of a request. The program now calls the model for step 4. What does the model know about steps 1 to 3?

Show the answer

Only what the program puts into the context for step 4. The model keeps nothing between calls; the program does the remembering by re-sending.

What is kept between steps 6 min

Within one request, the agent loop keeps a running list of everything that has happened: the messages, each tool call, each tool result. Before every model call, the program sends that whole list. In Python it is as plain as a list called messages that you append to after each step.

So the context grows with every step, and each call is larger than the last. Picture the assistant working on "Is the laser cutter free tomorrow at 3 pm, and do I need training?": the calendar result is added, then a page from the manual, then the training record. By the last call, the context holds all three.

Long runs can fill the window. Anthropic's engineering post describes three common remedies for work that outgrows it (Anthropic: Effective context engineering):

  • Compaction: when the context nears its limit, summarize the history and continue with the summary in place of the full text.
  • Structured note-taking: the agent writes notes to storage outside the context and reads them back when needed.
  • Sub-agents: a separate agent works on a sub-task in its own fresh context and returns a short result. You will meet this in a later lesson.
Anthropic also describes simply clearing out old tool results once they have been used, which the context-management announcement calls context editing (Anthropic: Managing context).

For a makerspace question, a request is short, a handful of steps, so you will rarely need compaction. What you will control is the size of each tool result. A tool that returns a whole 40-page manual puts 40 pages into every later call in that request.

Check yourself

The booking tool returns the full list of bookings for the whole month, though the student only asked about tomorrow. What is the best fix?

Show the answer

Make the tool return only the day asked about. Keep the context small at the source.

What is kept between sessions 6 min

A session here is one conversation with one student. When it ends, the program that held the messages list is done with it. On Tuesday, when the same student returns, a new request starts with an empty list. The model has no idea Monday happened.

A common mix-up

"The assistant is smart, so it will remember Sam from last week." It is tempting because chat products sometimes do appear to remember you. But that is because the product saves things and puts them back into the context. The model itself keeps nothing. If your program does not save and reload, nothing is remembered.

So memory, in an agent, means: information written to storage outside the model, which the program loads into a later context when it is useful. The storage can be as plain as a file or a database row. Anthropic's memory tool works this way: Claude asks to read or write files in a memory directory, and your application carries out each request against storage you control (Claude docs: memory tool). It is the agent loop again, with a tool whose job is notes.

Here is the makerspace example. At the end of Sam's visit, the program saves one short line:

students/sam.md
- Laser cutter: certified 2026-11-03
- 3D printer: not yet trained
- Prefers evening slots

On Tuesday, the program loads that file (a few dozen tokens) into the start of the context. Now the assistant can say "You are certified on the laser cutter, so I can book that" without asking. Note what was not saved: the full transcript, the manual text, and Monday's free calendar slots. The transcript is large and mostly noise; the manual can be searched again; and the slots are out of date by Tuesday.

Notes can be wrong. If a certification is revoked, an old note keeps saying "certified". For anything that matters, such as safety training, treat the authoritative record as the source and the note as a convenience, or give notes a date, as above.

Retrieval: finding the right page 6 min

The third kind of information is a long manual. A student asks, "Why is my laser cut scorching the edges?" The answer is on one page of a 60-page manual. You cannot put the manual in every context, and you should not. Instead you retrieve: search the manuals and put only the best matching passages into the context. When the passages are pasted in alongside the question, this is called retrieval-augmented generation, or RAG.

The steps, which you do once ahead of time and then on every question:

A chunk is a passage of a few hundred words, small enough to be specific and large enough to make sense alone. The index is what makes searching fast. There are two common ways to search it, and they fail in different ways:

  • Keyword search (for example BM25) matches the exact words. It finds "scorching" only if the manual says "scorching".
  • Embedding search turns each chunk into a list of numbers, an embedding, that captures its meaning, and finds chunks whose meaning is close to the question. It can match "scorching edges" to a page on "burn marks", but can miss exact names such as an error code.

Anthropic's write-up on contextual retrieval reports that combining the two beats either alone, that adding a short note to each chunk saying where it came from in the manual helps further, and that on their tests the failure rate for the top 20 results fell from 5.7% to 2.9% with those steps, and to 1.9% when a reranking step was added (Anthropic: Contextual Retrieval). Treat those exact numbers as their benchmark, not a promise for your manuals. The lesson for you is to test your own search on real student questions.

There is a second way to retrieve. Instead of the program searching before the model runs, you give the model a search_manuals tool and let it ask when it needs a page. Anthropic calls this just-in-time retrieval: the agent keeps light references and loads data into context only when it needs it (Anthropic: Effective context engineering). It costs a step but spares the context when no manual is needed, as in "Is the laser cutter free tomorrow?"

Check yourself

A student searches for "error E-42" on the 3D printer. The manual contains the exact text "E-42". Which search is most reliable for this question?

Show the answer

Keyword search, ideally combined with embeddings. Exact codes suit keywords; paraphrased questions suit embeddings.

Worked example and practice 3 min

Worked example: counting the input tokens in one request

Take the request "Is the laser cutter free tomorrow at 3 pm, and do I need training?" Assume the system prompt and tool descriptions together are 1,200 tokens and the question is 50, so the first call sends 1,250 tokens. Each tool call the model writes is about 50 tokens. Results: calendar 300, manual chunk 1,500, training record 100. Total input tokens over all four model calls?

  1. Call 1 sends the starting context: 1,250.
  2. Call 2 sends call 1's context plus the calendar call and result: 1,250 + 50 + 300 = 1,600. The earlier text is re-sent, not skipped.
  3. Call 3 adds the manual search and the chunk: 1,600 + 50 + 1,500 = 3,150.
  4. Call 4 adds the training lookup: 3,150 + 50 + 100 = 3,300.
  5. Add the four: 1,250 + 1,600 + 3,150 + 3,300 = 9,300 tokens. That is Figure 2.
Your turn

Same request, but the search tool returns the whole 6,000-token manual section instead of a 1,500-token chunk. Calls 1 and 2 are unchanged (1,250 and 1,600). Work out call 3 and call 4, then the total. Then say how many tokens the full-section design wastes compared with the chunk design.

Show a solution

Call 3: 1,600 + 50 + 6,000 = 7,650. Call 4: 7,650 + 50 + 100 = 7,800. Total: 1,250 + 1,600 + 7,650 + 7,800 = 18,300 tokens. That is 9,000 tokens more than the 9,300 of the chunk design, almost double, from a single oversized tool result, because it is re-sent on both later calls (4,500 extra tokens each time). Choosing what comes back from a tool is a cost decision.

Summary 1 min

  • The model sees only the context for one call, and keeps nothing between calls; the program re-sends the history.
  • Context grows each step and is billed each call, so keep tool results small and the prompt lean.
  • Between sessions, memory is information the program saves outside the model and loads back: short, stable and dated.
  • Long documents are retrieved in chunks, ideally by keyword and meaning together, rather than pasted whole.
